# Product registry

The existing website remains at `/`. Open `/admin` for product management. QR codes open public pages at `/p/<permanent-id>`.

## Local setup

1. Use Node.js 22 or later and run `npm install`.
2. Run `npm run catalog:setup`. This creates a random `ADMIN_SETUP_TOKEN` in the ignored `.env.local` file without overwriting existing settings.
3. Run `npm run dev` and visit `http://localhost:3000/admin`.
4. Copy the token from `.env.local` into the initial setup form, then choose an email and a password of at least 12 characters. Subsequent visits use the email and password only.
5. Add equipment from the dashboard, or import the Excel Master Sheet from Import / Export.

The initial database is empty. There are no default credentials or demonstration records. One administrator account is supported. Passwords use salted scrypt hashes; sessions expire after eight hours. Admin mutations require an authenticated session and a matching request origin. Login attempts are limited to ten per fifteen-minute window.

## Business rules

- Each record is one physical unit with its own QR code. Every field is optional.
- **QR Code Number**: a random (not sequential) 16-digit number generated by the registry when the record is created. It cannot be entered in the form or the spreadsheet, and it never changes on edit. The public scan page and manual lookup accept it.
- **Type of Product** (also the record title): five Complete ELB models (`ELB 24 V DC With/Without Hand Generator`, `ELB 110 V DC With/Without Hand Generator`, `ELB 110 V AC`) plus `Pedestal Unit`, `Locking Unit` and `Control Panel Unit`.
- A **Complete ELB** creates 5 records/QR codes: 1 Control Panel Unit, 2 Locking Units and 2 Pedestal Units. They share the Machine No., location, dates and service record, and remember the ELB model. Enter both Pedestal (and Locking) Numbers separated by a comma. A Complete ELB can only be added as a new entry; each of its 5 units is edited individually afterwards.
- Individual units use only their own number (Pedestal / Locking / Control Panel No.).
- **Zonal Railway / Division** come from the fixed list in `lib/railway.ts` (19 zones, 72 divisions, reflecting the South Coast Railway reorganisation). A division must belong to the chosen zone.
- **Warranty**: Date of Warranty Expiry = 2 years from the Date of Supply or 1 year from the Date of Installation, whichever is earlier. "Under Warranty?" is worked out against today's date (India time) every time a record is shown, so it switches to "No" automatically.
- **Service Record**: a list of dated entries; add rows in the form. In the spreadsheet, put one entry per line in the cell (`15-06-2025 - Annual maintenance done`).
- **Comments / Technical Notes**: separate entries added with "Add note"; each has a date (today by default), its own text and up to 8 images. A Comments column in an imported sheet becomes one note; older records' single comment appears as their first note. Exports list one note per line in the Comments column.
- Internal serial numbers (`PRD-000001`) come from the auto-increment primary key and are never reused. QR images contain a permanent random public identifier (`/p/<id>`).
- Deactivation keeps the record and changes the public page to “Equipment Record Inactive.” Reactivation restores it.
- Categories use trimmed, case-insensitive names. New railway records go into “Railway Equipment”.

## Excel Master Sheet

Download the template from Import / Export. Column order: `Machine No., Type of Product, Pedestal No., Locking No., Control Panel No., Zonal Railway, Division, Nearby Station, Version No., Date of Supply, Date of Installation, Date of Commissioning, Date of Warranty Expiry, Service Record`.

- Type of Product, Zonal Railway and Division are dropdowns; the Division list shows only the chosen zone's divisions (Excel named ranges + `INDIRECT`).
- Date columns accept real Excel dates and text such as `15-01-2025`, `15/01/2025` or `15-Jan-2025` (day first). Date of Warranty Expiry is a formula and is recalculated by the registry on import.
- Do not add QR Code Numbers. Rows whose QR Code Number, Complete ELB Machine No., or unit number is already registered are skipped as duplicates, so re-importing an export does not duplicate anything.
- Older column names (`Station Details`, `Locking Number`, `Type of ELB`, `Zone`, …) are still recognised.

Category header: `Category Name`.

Uploads support up to 5,000 rows. Preview performs no writes and shows how many QR codes each row will create. Commit validates again, skips duplicates in the database and the file, imports valid rows, and keeps a downloadable row report. Rows are written one at a time; a failure part-way leaves the earlier rows imported, and retrying skips them as duplicates.

Exports (.xlsx and .csv) use the Master Sheet column order followed by QR Code Number, Under Warranty?, ELB Model, LC Gate No., Comments, Public QR Link and Status. The .xlsx export keeps the dropdowns and formulas. Formula-like values in CSV are escaped for spreadsheet safety.

## Images and labels

Upload up to eight PNG, JPEG, or WebP images, each at most 5 MB. QR images can be downloaded as PNG or SVG. Product detail views include a print stylesheet for a 65 mm wide label. Use the browser's print scaling and paper settings appropriate to your printer.

## Deployment

The product registry supports Neon PostgreSQL (or other PostgreSQL databases) via `@neondatabase/serverless` when `DATABASE_URL` is set in `.env.local`:
```env
DATABASE_URL=postgresql://neondb_owner:...@...neon.tech/neondb?sslmode=require
```
When `DATABASE_URL` is provided, all categories, products, sessions, admins, and imports persist in Neon PostgreSQL. If `DATABASE_URL` is not provided, the registry falls back to local SQLite in `data/catalog.sqlite`.

Uploaded images live in `data/images` by default; set `CATALOG_DATA_DIR` to an absolute persistent directory to override it.

Set `APP_URL=https://your-final-domain.example` before generating production labels. It controls QR links, origin validation, and secure cookies. Preserve this domain for printed labels. Behind a reverse proxy, configure its public origin to match `APP_URL`. Serve production traffic over HTTPS.

Run `npm run build`, then `npm start`. Keep `.env.local` and the data directory private. Remove the setup token from production environment variables after the first admin has been created. Password recovery and additional admin roles are not included in this version.

## Verification

- `npm run test:catalog`: isolated database tests for zones and divisions, QR numbers, Complete ELB sets, warranty rules, Excel date handling, imports, updates, serial allocation, and exports.
- `npx tsc --noEmit`: TypeScript verification.
- `npm run lint`: repository lint. The existing website currently has unrelated lint errors in `app/about/page.tsx`, `AramcoHeader.tsx`, and `HeroSection.tsx`; the catalog files pass targeted lint.
- `npm run build`: production build.

The database tests use a temporary directory and do not touch the real catalog.

Browser verification is also available in `scripts/check-catalog-browser.mjs`. It uses installed Microsoft Edge (set `BROWSER_CHANNEL=chrome` for Chrome), creates test records, decodes the generated QR, and saves screenshots under `test-results/`. Run it only against an isolated local server. For example, in a separate PowerShell terminal:

```powershell
$env:CATALOG_DATA_DIR = Join-Path (Get-Location) '.catalog-test-browser'
$env:NEXT_BUILD_DIR = '.next-catalog-test'
$env:ADMIN_SETUP_TOKEN = 'catalog-browser-test-setup-token'
$env:APP_URL = 'http://127.0.0.1:3001'
npm run dev -- --hostname 127.0.0.1 --port 3001
```

Then run `node scripts/check-catalog-browser.mjs` from another terminal. Stop the isolated server afterward. These test environment settings must not be used for the real registry.
